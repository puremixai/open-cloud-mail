# 前端 UI / UX 审查 · 2026-09-05

后续实施状态见 [修改与验收记录](implementation.md)。以下保留修改前审查结论。

建议保留 Win95 的辨识度，把投入集中在可读性、操作语义、反馈完整性和响应式布局。复古的外观可以保留，交互需要满足今天的使用习惯。

本次为审查，不修改产品代码。检查范围包含登录、布局、Win95 桌面、收件箱与共享列表、邮件详情、写信、账户切换、个人设置，以及管理列表的部分实现。公开站点来自项目 `.env.remote` 中配置的 skymail.ink。浏览器验证覆盖公开登录页的桌面视口 1707×842 和手机模拟视口 390×844；站点需要登录，未进入账户或执行发送、删除、注册。登录后页面结论来自当前工作区代码，不能替代实际登录后的交互验收，也未确认线上构建与工作区完全相同。

证据截图：[桌面登录页](D:/VibeProjects/cloud-mail-private/docs/ui-ux-audit-2026-09-05/login-desktop.png)、[手机登录页](D:/VibeProjects/cloud-mail-private/docs/ui-ux-audit-2026-09-05/login-mobile.png)。浏览器模拟视口检查后已恢复。手机视口 documentElement.scrollWidth 与 innerWidth 均为 390，当前登录页无横向溢出；不代表软键盘和真机适配已通过。

优先级：P1 为影响理解、可用性或内容保留，应优先处理；P2 为效率和一致性提升；P3 为细节打磨。以下“目标”均为建议，未实施。

## 应保留的基础

- Win95 有明确配色、凸起/按下按钮样式和独立主题变量，不需要推倒重做。
- 邮件列表已有虚拟滚动、骨架屏、加载错误与重试入口；星标有乐观更新和失败回滚。
- 写信失败会重新显示编辑器，发送逻辑有防重复尝试机制，应在优化反馈时保留。
- 复制邮箱和验证码已有结果反馈；部分邮件投递状态已有文字、图标和警告条。
- Win95 已提供 focus-visible 虚线轮廓；部分动画已有 reduced-motion 样式。问题在于覆盖不完整，而非完全缺失。

## 统一视觉和交互标准

颜色应按用途管理：桌面背景、工作区、输入区、选中、hover、focus、正文、次要文字、成功、警告、危险。Win95 保留青绿桌面、灰色外框、深蓝标题与选中状态，邮件阅读区维持清晰层级；现代浅色与深色各自校准。不要一刀切清除复古主题的黑白硬边，也不要把所有状态压成同一种蓝色。

图标应通过同一个按钮组件统一热区、对齐、Tooltip、可访问名称、禁用和忙碌状态。16px 图形不意味着 16px 按钮；悬停提示也不能代替可访问名称。星标至少区分未收藏、已收藏、提交中和失败回滚。

排版可采用 12/14/16/20px 的有限层级，主体中文字体优先可读；配额、时间和计数使用等宽数字。邮件产品不宜为了视觉花样增加纹理、打散对齐或扩大所有留白。边框用于定义复古窗口与控件，正文内部尽量减少重复边框。

动效建议将普通反馈控制在约 120–180ms，抽屉与弹层约 180–240ms，按下即时反馈。无需给所有元素加缩放；密集邮件列表更适合背景和状态变化。以上时间是设计建议，最终根据连续操作观感调整。

反馈规范应区分动作已接收、执行中、完成、失败可恢复。刷新已有列表时保留旧内容并标明更新中；删除成功若支持恢复，提供短时撤销。若后端不能恢复，不应仅做一个假撤销按钮。表单错误贴近字段；离开写信页时说明内容是否保存。

## 建议实施顺序

1. 第一批：草稿关闭语义、内容保留、键盘与按钮热区、登录对比度、回收站真实语义。优先解决误操作和不可用。
2. 第二批：统一 IconButton 和语义色；按容器适配列表密度；明确批量选择范围与发送状态。
3. 第三批：普通用户搜索、空状态、字段级反馈、自动填充、动效和主题一致性。

搜索、草稿同步、回收站恢复和删除撤销可能涉及接口与后端能力，不应归类为纯 CSS 修改。先完成组件级规范，再让页面复用，避免每页单独微调。
